# ShotStudio — Glossary

ShotStudio is a single-tenant, one-time-pay tool that turns three raw mobile screenshots into a polished three-image App Store screenshot set. Section headers show the area each term belongs to. Code wins over this file: if they disagree, fix this file.

## Language

### Generation

- **Generation** — A single end-to-end job that produces one Set of three Shots from one Brief. _Avoid_ "render", "job", "run".
- **Brief** — What the user gives one Generation: app name, pitch, audience, Category, Style Preset and Reference Screenshots. _Avoid_ "request", "payload", "input".
- **Set** — The three-Shot deliverable returned by one Generation. _Avoid_ "screenshot set", "image set", "output", "bundle", "pack" (Pack means a Credit Pack).
- **Shot** — One of the three images in a Set, generated by the AI; each has a Shot Role. _Avoid_ "image", "panel", "frame", "output image".
- **Shot Role** — One of `hero_feature`, `differentiator`, `another_feature`; determines the prompt and which Reference Screenshot is used. _Avoid_ "shot type", "slot".
- **Reference Screenshot** — A user-uploaded raw mobile screenshot fed to the model as image-to-image input for one Shot. _Avoid_ "input image", "source image", "uploaded screenshot".
- **Style Preset** — One of the named personalities in `src/lib/generation/presets.ts` (`friendly`, `professional`, `minimal`, `bold`) bundling typography and headline voice. Theme and palette come from the Reference Screenshots, not the preset. _Avoid_ "theme", "style", "look".
- **Category** — The app's App Store category; maps to a default Style Preset that the user can override. _Avoid_ "vertical", "genre".
- **Pending Generation** — A Generation row whose `status = 'pending'` — Credit already debited, work in flight. _Avoid_ "in-progress generation", "running job".
- **Abandoned Generation** — A Pending Generation with no outcome more than 10 minutes after it started; the sweep fails and refunds it. _Avoid_ "stuck", "orphaned", "stale generation".

### Billing

- **Credit** — The unit of account. 1 Credit = 1 Generation. Credits never expire and are not refundable except via failed-Generation Refund. _Avoid_ "token", "shot credit".
- **Credit Ledger** — Each User's Credit balance plus their Transactions; changes only through Debit, Grant and Refund. _Avoid_ "wallet", "balance table".
- **Credit Pack** — A purchasable bundle of Credits at a fixed price (`starter`, `growth`, `studio`). _Avoid_ "plan", "tier", "package" (the type is named `CreditPackage`, but in conversation prefer "pack" — "package" collides with the pnpm sense).
- **Transaction** — A row in the Credit Ledger recording a Credit movement of type `purchase`, `usage`, or `refund`. _Avoid_ "ledger entry", "credit event".
- **Grant** — The operation that credits a Pack's Credits to a User after a successful Stripe checkout; idempotent on `stripePaymentId`. _Avoid_ "issue", "top-up".
- **Debit** — The operation that removes one Credit and writes a `usage` Transaction, always in the same database transaction as the Pending Generation it pays for (`debit` in `src/lib/credits.ts`). _Avoid_ "charge", "spend", "consume".
- **Refund** — The operation that returns one Credit when a Generation fails or is abandoned, exactly once, together with the Generation's move from `pending` to `failed`. _Avoid_ "reverse", "rollback".
- **Checkout Session** — The Stripe-hosted payment page created by `/api/checkout`; its `id` is reused as the `stripePaymentId` on the resulting Grant. _Avoid_ "payment session".
- **Delivery Claim** — The short-lived Redis mark that lets only one delivery of a Stripe event run at a time. _Avoid_ "lock", "idempotency key" (that means Resend's keys).

### Identity

- **User** — An authenticated Clerk identity with a mirrored `users` row holding the Credit balance. Single-tenant: no orgs, no teams. _Avoid_ "account", "customer" (Stripe Customer is a different thing).
- **User Email** — The email stored on the User row: Clerk's primary email address, or the first address when no primary is set. Stripe's payment email is written only when no User row exists yet. _Avoid_ "billing email", "contact email".
- **JIT User Sync** — The `ensureUser` upsert called on every authenticated entry point so a User row exists before any Billing or Generation work; closes the Clerk-vs-Stripe webhook race. _Avoid_ "user provisioning", "user bootstrap".
- **User Anonymization** — On Clerk `user.deleted`, or when a new User's email is held by a row whose Clerk account no longer exists, replacing email with `deleted+<id>@anonymized.local` and nulling `stripeCustomerId` instead of deleting the row, to preserve the financial audit trail. _Avoid_ "user deletion", "user purge".

## Relationships

- A **User** has a Credit balance (integer) and a history of **Transactions**, together the **Credit Ledger**.
- A **User** has many **Generations**; each Generation belongs to exactly one User and is started from one **Brief**.
- A **Generation** produces one **Set** of three **Shots**; each Shot has one **Shot Role** and consumes one **Reference Screenshot**.
- A **Generation** is configured by exactly one **Style Preset** and one **Category**; Category determines the default Style Preset.
- A **Debit** writes a `usage` Transaction in the same database transaction that creates the Pending Generation it pays for.
- A successful Generation moves to `complete`; a failure or an **Abandoned Generation** moves to `failed` together with one **Refund**, which writes a `refund` Transaction.
- A **Grant** writes a `purchase` Transaction whose `stripePaymentId` equals the **Checkout Session** id; the **Delivery Claim** keeps two deliveries of the same Stripe event from running at once.
- A **Credit Pack** maps to a Stripe Price; on `checkout.session.completed` the Pack's `credits` are Granted to the User identified by `metadata.userId`.

## Example dialogue

> **PM:** "Mira just paid for the Growth pack but her balance still shows 0 — what's going on?"
>
> **Eng:** "Stripe webhook delivery hasn't landed yet. The Checkout Session completed on Stripe's side, but our `checkout.session.completed` handler is what calls `grant`, and that's what bumps her Credit balance. If she refreshes in a few seconds it should be there — and the Grant is idempotent on the session id, so even if Stripe retries we won't double-credit her. If it's been minutes, look in the Stripe dashboard for the event id and check the webhook logs."
>
> **PM:** "Got it. And if her Generation fails halfway through?"
>
> **Eng:** "The Generation moves from `pending` to `failed` and her Credit is Refunded in the same step, so her balance ends up where it started. If the request dies before that, the sweep picks it up as an Abandoned Generation after 10 minutes."

## Flagged ambiguities

- **"Screenshot"** — Used in two senses: a **Reference Screenshot** (raw user-uploaded mobile screenshot, _input_) versus an App Store screenshot in the colloquial / marketing sense (the _output_, which we call a **Shot**). UI copy in `wizard.tsx` and `how-it-works.tsx` says "screenshot" for input; FAQ and hero copy say "screenshot" for output. In code, prefer "Reference Screenshot" for input and "Shot" for output.
- **"Set"** — Marketing copy and Pack pricing UI use "set" (`pluralize(p.credits, "set")`) as a synonym for "Credit", e.g. "10 sets". Internally, a Set is the _output_ of a Generation, not a unit of account. The 1:1 mapping (1 Credit → 1 Generation → 1 Set) makes the slippage harmless, but copy that says "Buy 4 sets" really means "Buy 4 Credits". Keep the data model wording (`credits`) distinct from the user-facing wording ("sets") in conversation.
- **"Hero"** — Overloaded. In Marketing it means the landing-page hero section. In Generation it means the `hero_feature` Shot Role (the first Shot in the Set).
- **"Generation"** — Used for (a) the verb/act of generating (`generate()`), (b) the DB row (`generations` table), and (c) loosely for the Set it produces. Prefer **Generation** for the row/job and **Set** for the deliverable.
- **"Package" vs "Pack"** — The TypeScript type is `CreditPackage`, the variable is `pack`, the marketing UI says "pack". Prefer "Credit Pack" in conversation; "package" collides with pnpm's sense. The code naming asymmetry is not worth refactoring.
- **"Customer"** — Stripe uses "Customer" for its own object; we don't model Customers in our schema (only `stripeCustomerId` on the User). Don't say "customer" when you mean "User".
